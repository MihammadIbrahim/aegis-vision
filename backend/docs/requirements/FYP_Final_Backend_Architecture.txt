# PART 1: The Big Picture (Teeno Architectures Ka Sangam)

Aapke project mein 3 architectures alag alag nahi hain, balki yeh **3 mukhtalif levels (Zoom Levels)** par kaam kar rahi hain:

```
+---------------------------------------------------------------------------------------+
|  LEVEL 1: SYSTEM / MACRO LEVEL  ---> MICROSERVICES ARCHITECTURE                       |
|  (Workloads ko unki computational nature [GPU vs CPU vs I/O] ke hisab se alag karna)   |
+---------------------------------------------------------------------------------------+
                                           |
                                           v
+---------------------------------------------------------------------------------------+
|  LEVEL 2: COMMUNICATION / MESO LEVEL ---> EVENT-DRIVEN ARCHITECTURE (EDA)             |
|  (Services aapas mein direct HTTP call nahi karengi, RabbitMQ ke events se chalengi)   |
+---------------------------------------------------------------------------------------+
                                           |
                                           v
+---------------------------------------------------------------------------------------+
|  LEVEL 3: CODE / MICRO LEVEL    ---> CLEAN ARCHITECTURE (HEXAGONAL / DDD)             |
|  (Har single service ke andar business logic framework aur database se azad hogi)     |
+---------------------------------------------------------------------------------------+
```

# PART 2: Microservices Breakdown (Requirements Ke Mutabiq)

Surveillance system mein har kaam ka nature mukhtalif hota hai. Agar sab kuch aik backend mein daal diya jaye toh GPU ka model chalte hi poora system hang ho jayega. Is liye humne 7 decoupled services banayi hain:

### 1. `core_api` (FastAPI Main Business & Identity Service)
* **Kyun Alag Hai?** Yeh service sirf lightweight HTTP REST requests handle karti hai (Logins, CRUD, Permissions, Organization Hierarchy, User records). Isme koi heavy video ya AI processing nahi hoti, is liye yeh **99.99% uptime** aur **<20ms response time** degi.
* **Requirements Mapped:**
  * Multi-Tenancy (Org -> Branch -> Building -> Floor -> Area -> Camera).
  * RBAC & User Management (Super Admin, Main Admin, Branch Admin, Supervisor, Guard).
  * 2FA Authentication (Brevo Email OTP) & Self-Service Password Reset.
  * System IDs Generation (`ADM-`, `SUP-`, `GRD-` + 11 digits) & Password-protected ID regeneration.
  * Rejoining System (Duplicate banaye baghair purana record restore karna).

### 2. `video_ingestion` (High-Throughput Streaming Engine)
* **Kyun Alag Hai?** IP cameras continuous 24/7 RTSP video packets bhejte hain. Yeh **I/O-Intensive (Disk & Network)** kaam hai. 
* **Requirements Mapped:**
  * OpenCV / GStreamer ke zariye multiple RTSP IP camera streams pull karna.
  * **Frame Sampler:** 30 FPS video ko 5 ya 10 FPS par sample karna taake AI GPU overload na ho.
  * **Segmented Video Writer:** Continuous video ko 1-minute MP4 chunks mein tor kar seedha Dedicated SSD array `/mnt/cctv_storage/recordings/` par stream karna.

### 3. `cv_inference` (Heavy AI Worker Pool)
* **Kyun Alag Hai?** Yeh **GPU & Compute-Intensive** kaam hai. Isme PyTorch, CUDA, aur TensorRT chalte hain jo 100% GPU VRAM use karte hain.
* **Requirements Mapped:**
  * **Human Detection & Tracking:** YOLOv8 + ByteTrack (Camera view mein temporary track IDs maintain karna).
  * **Weapon Detection:** Gun/Knife detection (Automatic High-Priority Alert generate karna).
  * **Fight / Violence Detection:** 16-frame sequence analysis temporal models ke zariye.
  * **Cross-Camera Re-ID:** Detected person ka 512-D vector embedding nikalna taake Person Search mein use ho sakay.
  * **Restricted-Area Face Recognition:** Whitelisted facial embeddings ke sath match check karna.

### 4. `alert_notification` (Smart Alert & Dispatch Engine)
* **Kyun Alag Hai?** Jaise hi AI detection hoti hai, decision lena ke kis guard ko notification jana chahiye.
* **Requirements Mapped:**
  * **Priority Engine:** Weapon aur Fight detections ko instantly **High Priority (RED)** mark karna.
  * **Location Matcher:** Camera ka physical location (Building A, Floor 2) check karke wahan assigned active guards ko filter karna.
  * **Dispatchers:** Guard Mobile App par Firebase Cloud Messaging (FCM) push notification bhejna aur Web Dashboard par alert popup phenkna.

### 5. `incident_chat` (Real-Time Coordination WebSockets)
* **Kyun Alag Hai?** Chatting continuous open socket connections mangti hai. Agar 50 guards aur supervisors aapas mein baat kar rahe hain, toh normal REST API thread pool choke ho sakta hai.
* **Requirements Mapped:**
  * Alert/Incident specific isolated chat rooms.
  * Role-based message identification ("Supervisor Ali", "Guard Ahmed").
  * Supervisors ke directives guards tak real-time deliver karna.
  * Complete chat audit history timestamp ke sath retain karna.

### 6. `ai_rag_and_agent` (Security Assistant & Investigation Agent)
* **Kyun Alag Hai?** LLM calls (OpenAI/Anthropic/Local LLMs) time-consuming hoti hain (2 se 5 seconds lagte hain). Isko alag asynchronous microservice hona chahiye.
* **Requirements Mapped:**
  * **RAG Security Assistant (Layer 2):** Approved security manuals aur SOP PDFs ko chunk karke `pgvector` mein store karna aur policy-grounded answers dena with clickable citations.
  * **Agentic Investigation Workflow (Layer 3 - LangGraph):** Incident metadata + evidence clips + SOP manual ko utha kar evidence-based summary banana.
  * **Mandatory Human Approval Checkpoint:** AI kabhi bhi autonomously kisi ko criminal declare nahi karega; consequential actions se pehle Supervisor ka approval button lazmi hoga.

### 7. `storage_retention_daemon` (SSD Disk Lifecycle Manager)
* **Kyun Alag Hai?** 24/7 chalne wala background lightweight cron service jo disk ko full hone se bachata hai.
* **Requirements Mapped:**
  * Normal CCTV footage ko configured retention duration (Minutes/Hours/Days) ke baad delete karna.
  * **Strict Evidence Protection:** `/mnt/cctv_storage/evidence/` ko kabhi delete nahi karega (Evidence tab tak preserve rahegi jab tak Admin manually delete na kare).
  * SSD capacity 85% se barhne par dashboard par warning trigger karna.

# PART 3: The Event-Driven Flow (RabbitMQ Choreography)

System mein **tight coupling** khatam karne ke liye services aik doosre se direct synchronous baat nahi karti, balki **Events** publish aur consume karti hain.

### Complete Real-Life Incident Trace: "Gate 1 par Weapon Detect Hua"

```
[ IP Camera 01 (Gate 1) ]
         │ (Continuous RTSP Stream)
         ▼
[ 1. Video Ingestion Service ]
         │
         ├───► Writes 1-min raw chunk ──────► [ Dedicated SSD: /recordings/... ]
         │
         └───► Extracts 5 Frames/sec
               Publishes Event: `camera.frame.captured`
                     │
                     ▼ (RabbitMQ Topic Exchange: `cctv.events`)
                     │
[ 2. CV Inference Service (GPU Worker) ]
         │  - Consumes `camera.frame.captured`
         │  - Runs YOLOv8 Weapon Detector -> Finds "Pistol" (Confidence 0.91)
         │  - Saves snapshot crop to `/mnt/cctv_storage/evidence/snap_101.jpg`
```

# PART 4: Clean Architecture Inside `core_api` (Code Level)

Har service ke andar humne **Clean Architecture (Hexagonal / Onion)** implement ki hai. Iska matlab hai code 4 concentric circles mein divided hai:

```
               +-------------------------------------------------+
               |  4. PRESENTATION LAYER (FastAPI Routers, DTOs)  |
               |       +---------------------------------+       |
               |       |  3. INFRASTRUCTURE LAYER        |       |
               |       |     (PostgreSQL, Brevo, Rabbit) |       |
               |       |       +-----------------+       |       |
               |       |       | 2. APPLICATION  |       |       |
               |       |       |    (Use Cases)  |       |       |
               |       |       |       +-------+ |       |       |
               |       |       |       |1. DOMAIN|       |       |
               |       |       |       +-------+ |       |       |
               |       |       +-----------------+       |       |
               |       +---------------------------------+       |
               +-------------------------------------------------+
```

### Layer 1: Domain Layer (`core_api/src/domain/`)
* **Entities:** `user.py`, `alert.py`, `camera.py`, `incident.py`.
* **Khas Baat:** Is layer mein **0% external libraries** hain (na FastAPI, na SQLAlchemy, na PyTorch). Yahan sirf pure Python classes hain.
* **Business Rule Example:** Guard jab remove hota hai, uska status `Left` hoga aur login disable hogi, lekin history delete nahi hogi. Yeh rule entity ke andar likha hota hai.

### Layer 2: Application Layer (`core_api/src/application/`)
* **Use Cases:** Har requirement ka aik single use-case file hai (e.g. `rejoin_guard.py`, `verify_email_otp.py`, `acknowledge_alert.py`).
* **Interfaces (Ports):** Yeh layer batati hai ke hume kya chahiye: `IEmailService`, `IAlertRepository`, `IEventPublisher`. Isko yeh nahi pata ke email Brevo bhej raha hai ya Gmail.

### Layer 3: Infrastructure Layer (`core_api/src/infrastructure/`)
* **Adapters:** Yeh Application Layer ke interfaces ko asal mein implement karti hai:
  * `brevo_email_service.py` -> Brevo API ko call karke OTP bhejti hai.
  * `alert_repository_impl.py` -> PostgreSQL mein actual SQL queries chalati hai.
  * `rabbitmq_publisher.py` -> RabbitMQ exchange par JSON publish karti hai.
* **Fayda:** Kal ko agar university bole ke "Postgres chor kar MongoDB use karo", toh aapko sirf yeh aik folder change karna hoga. Domain aur Application logic ko haath bhi nahi lagana parega.

### Layer 4: Presentation Layer (`core_api/src/presentation/`)
* **FastAPI Routers:** HTTP requests receive karti hain, Pydantic se validate karti hain, aur seedha relevant Use Case ko pass kar deti hain.
* Yahan aapke project ke **saare 19 Routers** mojood hain jo aapke 25 Admin screens, 8 Super Admin screens, aur 10 Guard screens ko 1-to-1 support karte hain.

# PART 5: Dedicated SSD Storage & Retention Design

CCTV project ka sab se bara practical masla disk bandwidth hota hai. Is architecture mein disk ko 2 hisso mein split kiya gaya hai:

```
/mnt/cctv_storage/ (Mounted Dedicated Fast NVMe/SSD Array)
│
├── ├── recordings/                     <-- [TIER 1: VOLATILE ROUTINE STORAGE]
│   └── {org_id}/{branch_id}/{cam_id}/
│       └── 2026-10-26/
│           ├── chunk_1400.mp4          (1-minute segment)
│           └── chunk_1401.mp4          (Auto-deleted after configured retention)
│
└── ├── evidence/                       <-- [TIER 2: PERMANENT INVESTIGATION VAULT]
    └── {org_id}/{incident_id}/
        ├── weapon_detected_frame.jpg   (High-res snapshot)
        ├── 20s_incident_clip.mp4       (Critical incident video)
        └── guard_manual_report.jpg     (Guard's mobile photo proof)
```

### Yeh Kaise Kaam Karta Hai?
1. **Zero Database Overload:** Video files PostgreSQL ke andar store **nahi** hotin. DB mein sirf file ka string path hota hai.
2. **Auto-Purge Safety:** `storage_retention_daemon` har 5 minute baad check karta hai. Agar retention duration 24 hours set hai, toh 24 hours purane chunks `/recordings/` se unlink (delete) ho jayenge.
3. **Evidence Immunity:** Jab bhi koi AI alert create hota hai ya guard manual report submit karta hai, footage `/evidence/` vault mein copy ho jati hai. Retention daemon is folder ko **touch bhi nahi karta**. Yeh tab tak rahegi jab tak Admin password daal kar khud delete na kare.

# PART 6: AI Training (`ml_training/`) vs Runtime Serving (`cv_inference/`)

Aap ne pucha tha ke model train kaise hoga aur backend disturb kyun nahi hoga:

```
[ OFFLINE RESEARCH: ml_training/ ]                       [ PRODUCTION RUNTIME: services/cv_inference/ ]
│                                                        │
├── 1. Download Datasets (CrowdHuman, Weapons)           │
├── 2. Run train_weapon_detector.py                      │
├── 3. Evaluate mAP & Precision                          │
└── 4. Export PyTorch (.pt) ──► convert_to_onnx.py       │
                                         │               │
                                         │ (best.onnx)   │
                                         └───────────────┼──► Loaded into /weights/ folder
                                                         │    - BaseDetector dynamically loads ONNX
                                                         │    - Real-time 60 FPS CUDA Inference
                                                         │    - Zero-downtime model swap
```
* **Kyun Best Hai?** Training ke dauran agar GPU 100% compute par 12 ghantay chalta rahay, tab bhi live CCTV streaming, Guard chat, aur Web dashboards **1 millisecond ke liye bhi slow nahi honge**.

# PART 7: Kubernetes Production-Readiness (`k8s/`)

Production deployment ke liye Kubernetes manifests ko Kustomize pattern par arrange kiya gaya hai:
* **GPU Node Scheduling:** AI inference pods ko sirf un nodes par bhejta hai jahan NVIDIA GPUs lage hain (`node-selector.yaml`).
* **High-Speed Storage Mounting:** Dedicated physical SSD ko `PersistentVolume` ke zariye pods mein mount karta hai with `ReadWriteMany` permissions.
* **KEDA Autoscaler:** Agar camera par achanak multiple fights ya weapons detect hone lagain aur RabbitMQ queue barhne lage, toh K8s automatically AI worker pods ko scale-up (2 se barha kar 5 ya 10) kar deta hai.
* **WebSocket Ingress:** Guard mobile chat aur live dashboard alerts ke liye TCP connection timeout aur sticky session affinity provide karta hai.
